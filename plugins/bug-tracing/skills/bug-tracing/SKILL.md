# 先数据后代码

用户调用时带了参数，参数在用户消息里，也填进 `$ARGUMENTS`。

- 参数是错误信息或现象：从第 1 步走。
- 参数是接口名或功能名：从第 2 步走。
- 无参数：先问清现象、期望结果与复现步骤，再动手。

## 排查六步

1. **复现与定界。** 问清并写下来：现象是什么、期望是什么、范围有多大（哪一端、哪个环境、哪个账号或区域）、必现还是偶发、最近改了什么。范围没定住就动手，越查越大。
2. **先查数据。** 优先怀疑数据本身，而不是代码：字段是不是空的、旧的、缺的、重复的、格式不对的；软删除标记对不对；上游有没有同步过来；是不是写进一个库、读的是另一个库；单位、精度、时区、编码有没有偏差；缓存与库是否一致。疑点清单见 `references/data-source.md`。这一步多数问题就能定位，不需要读代码。
3. **需要时连库取证。** 先问清库环境、库名、数据库类型（虚谷还是 MySQL），得到允许再连。只跑 `SELECT`，按库类型加分页限制（MySQL 用 `LIMIT`，虚谷用 `ROWNUM` 或 `FETCH`），把查询与返回的关键几行记下来当证据。流程见 `references/data-source.md`。
4. **数据排除干净，再读代码。** 数据核实无误，才沿调用链往下走：控制层取参与校验、服务层分支与事务、数据访问层的条件与字段、出口有没有被二次加工。逐段核对入参是什么、出参应该是什么、实际是什么。重点看分支遗漏、异常被吞、默认值、空值与边界、并发、缓存与事务提交。读法见 `references/tracing.md`。
5. **证据对齐。** 把库里的数据、日志、请求报文按时间串起来，指出**第一处不符合预期**的位置。那是问题的起点，最后那处报错往往只是后果。
6. **给结论。** 说清根因、证据、影响范围与修复方向。结论只在会话里给，不写文件；用户要留档再写。

## 什么时候不用

根因已经明确、只需按结论改代码时直接改，不用再走六步。六步用于现象不对、原因不明的时候。

## 三条硬规矩

1. **先数据后代码。** 数据没核实清楚，不许先怀疑代码。数据问题更常见，也更容易在几分钟内证伪或证实。
2. **数据库只读。** 只跑 `SELECT`；`UPDATE`、`DELETE`、DDL 与存储过程调用一律停下问用户。
3. **结论落在第一处不符合预期**，不许停在最后那个报错上。

## 红线

- 不拿日志里的一行报错当结论。
- 不凭记忆写表名、字段名；先看 mapper、实体类或建表语句。
- 读不懂的代码段落就说读不懂，不要编一套逻辑出来。
- 连库前环境、库名、数据库类型三项缺一项都不动手；生产库要用户明确许可。
- 手机号、身份证、详细地址这类字段不取进结果，需要比对时只看位数或掩码。
