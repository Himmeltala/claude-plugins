# 代码架构：管复杂度，不管一次写对

目标只有一个：降低认知负荷与变更成本，让代码随需求可预测地演进。UI、接口、团队都会变，设计围着变化转，不围着“这次能跑”转。

## 四支柱

1. **清晰边界**：模块、组件、状态、副作用各有明确归属。一个单元只有一个变化原因，对外只暴露小而稳定的接口。
2. **可预测的数据流**：单一数据源，单向流动；能派生就不存储；异步与副作用集中在边界。
3. **组合优于配置与继承**：用组合表达变化，不用布尔开关堆分支；先有两个具体实现作证据，第三次出现再抽象。
4. **质量约束前置**：可测试性、性能、可访问性、错误处理在设计时定，不留到上线前。

一句话：**清晰边界 + 单向数据流 + 最小状态 + 可组合契约 + 可测试性**。

## 判断顺序

1. 定位变化点：这次需求变的是展示、交互、数据，还是规则？
2. 看边界：变化会不会越过现有模块或组件接口？
3. 看状态：新数据是存储还是派生？归谁所有？生命周期多长？
4. 看抽象：现有抽象是否挡住变化？没有两个以上具体实现，先不抽象。
5. 定验收：核心逻辑能否脱离 UI 测试？失败路径是否明确？

## 常见症状与先查什么

| 症状 | 先查 |
|---|---|
| 改一个功能要动很多文件 | 边界是否按变化原因划分 |
| 状态对不上、刷新后不一致 | 是否有多个数据源、隐式双向同步 |
| 模块参数越加越多 | 是否该用组合替代配置 |
| 同一段逻辑复制多次 | 是否已到第三次，能否抽出稳定接口 |
| 逻辑难以单独测试 | 业务逻辑是否与外部依赖耦合 |
| 新人看不懂主流程 | 副作用是否散落，主链路是否被细节淹没 |

## 反模式

全局状态滥用、组件过大、副作用散落、隐式数据同步、过度抽象、业务逻辑与 UI 纠缠、为不存在的未来预留扩展点。

## 分诊

- 前端实现问题（组件拆分、状态归属、请求层、按功能分包）优先走 `frontend-architecture`，不要停在本文。
- 后端等有真实需求再建技能，不提前写空规则。

## 评审三问

1. 这次改动影响的最小单元是什么？契约变了吗？
2. 新状态归谁所有？生命周期是否清楚？
3. 失败与空数据路径是否有明确归属？

前端组件、状态与请求层的细化问题，交给 `frontend-architecture`。
