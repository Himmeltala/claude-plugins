# 边界

边界的判据只有一条：**一个单元只有一个变化原因**。边界画错，后面所有设计都会被拖累。

## 模块边界

- 按变化原因切分，通常就是按业务能力切分；不按文件类型把同一业务拆散。
- 目录结构以项目现状为准，不为了套某种模板迁移或改名。feature-first 是判据，不是目录模板。
- 每个业务模块只暴露一个小而稳定的入口：页面、少量组件、组合函数。
- 跨模块只走公开入口，不直接引用对方内部文件。
- 两个模块都要用的东西才进共享区；只有一个模块用的，留在原地，等第二次出现再提升。

按功能分包的判断只有两条：

1. 同一业务的变化，涉及的文件是否聚在一起？
2. 跨业务共享，是否只有一个稳定入口？

示意结构，按实际项目调整：

```text
src/
  <业务>/{组件,组合函数,请求,类型}
  shared/{通用组件,通用函数,请求基础设施}
  app/{路由,全局状态,布局}
```

## 组件边界

按职责分三类，不要混：

| 类型 | 职责 | 依赖 |
|---|---|---|
| 展示组件 | 只根据输入渲染，不取数、不改全局状态 | 只依赖输入参数与样式 |
| 业务组件 | 编排交互与数据，组合展示组件 | 可依赖组合函数、全局状态容器、service；不直接创建 HTTP 客户端 |
| 基础组件 | 按钮、输入框、弹层等通用件 | 不依赖业务 |

组件边界看变化原因：样式与布局变化落在展示组件；交互流程变化落在业务组件；业务规则变化沉到纯函数模块，业务组件只调用。

## 状态边界

- 一个字段只有一个所有者。所有者负责创建、更新、销毁。
- 所有权跟生命周期走：随组件生灭的放组件内，跨路由存活的才上全局。
- 全局状态只存“跨路由存活且多个不相关页面都要读写的业务事实”，不存 UI 临时态（展开、选中、悬停）。
- 派生状态不另存一份，避免两个写入点。

## 副作用边界

请求、路由跳转、本地存储、计时器、事件订阅、日志，都算副作用。各自只能有一个出口：

- 请求：请求层模块。组件不直接调 HTTP 客户端。
- 路由：路由模块或页面级入口。组件不猜当前路径。
- 本地存储：存储适配层。业务代码不直接碰 `localStorage`。
- 订阅与计时器：创建它的地方负责清理。

## 依赖方向

```text
页面与路由
  → 业务组件
    → 组合函数、全局状态容器、service
      → 请求层
        → 类型与纯工具
```

箭头单向。下层不得反向引用上层；同层模块之间尽量不互相引用，需要共享就下沉到更稳定的层。组件不直接创建 HTTP 客户端；请求层只被组合函数、全局状态容器、service 调用。

## 检查清单

1. 这个文件属于哪个业务模块？跨模块引用走公开入口了吗？
2. 这个组件的变化原因只有一个吗？
3. 这个状态字段的所有者是谁？生命周期多长？
4. 副作用是否有唯一出口？失败路径归谁处理？
5. 新加的依赖是向上还是向下？
