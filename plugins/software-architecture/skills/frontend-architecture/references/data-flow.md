# 数据流

目标：任何时刻都能回答“这个值从哪来、谁能改、什么时候失效”。

## 单一数据源

- 同一事实只存一份。用户信息、权限、当前选中项、列表数据，都只有一个所有者。
- 需要多份视图时，从同一份源派生，不复制成两份状态再手动同步。
- 状态结构扁平化：列表存 `byId` 加 `ids`，避免嵌套深处更新与重复副本。

## 派生优先

- 能从现有状态算出来的，不存。总数、过滤结果、是否为空、按钮是否可用，都用计算值。
- 不用监听器把 A 写到 B。监听器回写会制造第二个写入点，最终形成循环与抖动。
- 表单分两层：编辑中的草稿留在组件内，提交成功后才写入全局状态。不要把每次击键写进全局状态容器。

## 异步与错误

请求层统一返回可判别的结果，组件按状态渲染：

```ts
type AsyncState<T> =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'success'; data: T }
  | { status: 'error'; error: AppError }
  | { status: 'empty' }
```

规则：

- 请求函数只负责发请求、解析、归一化错误，不碰组件状态。
- 组件或组合函数负责把结果放进 `AsyncState`。
- 错误统一归一化成一种结构（码、用户可读信息、是否可重试），不让组件猜后端返回格式。
- 并发请求要处理竞态：只接受最后一次请求的结果，或用请求标识丢弃过期响应。
- 取消与超时明确归属，不留下永远 `loading` 的状态。

## URL 是状态

以下数据放 URL，不放全局状态容器：

- 刷新后应保留：筛选条件、分页、排序、当前标签页。
- 可分享、可前进后退：搜索词、详情页标识。
- 不放 URL：大对象、敏感信息、频繁变化的临时态。

URL 变化驱动数据加载，而不是组件挂载时读一次再自己维护副本。

## 写入规则

- 全局状态容器的写入方法是唯一写入点；组件只读，通过写入方法改。
- 跨组件同步用显式事件或状态写入方法，不用双向绑定隐式传导。
- 派生值放在读取侧计算，不放在写入侧维护。

## 检查清单

1. 这个值能否从现有状态算出来？能就不存。
2. 有几个地方能改它？多于一个就收敛。
3. 刷新页面后它应该保留吗？应该就放 URL。
4. 请求失败、超时、空数据分别渲染什么？
5. 快速切换条件时，旧响应会不会覆盖新响应？
