# 质量门禁

质量不是上线前补的，是设计时定的。四项：可测试性、性能、可访问性、错误处理。

## 可测试性

- 业务规则写成纯函数：输入明确，输出明确，不读全局、不发请求。
- 请求通过参数注入，不在函数内部直接创建客户端；测试时替换成假实现。
- 数据转换与数据获取分开：取数函数只取数，转换函数只转换。
- UI 测试只覆盖交互与渲染分支；规则测试留在纯函数层。
- 测试写不动，通常不是测试框架问题，是业务逻辑与 UI、请求耦合了。

## 性能

先测量，再优化。没有数据支撑的优化就是猜。

- 长列表用虚拟滚动；首屏外的重组件按需加载；路由级代码分割。
- 避免无原因的重复渲染与重复计算；缓存要有失效策略。
- 图片按尺寸与视口加载；字体做子集化、按需字重，并设置 `font-display`。
- 不要为了“可能慢”提前加缓存与记忆化，先找出真实瓶颈。

## 可访问性

- 用语义元素：按钮用按钮，链接用链接，标题按层级。
- 键盘可达：焦点顺序合理，焦点可见，弹层打开后焦点进入，关闭后回到触发点。
- 表单控件有可读标签；错误信息与控件关联。
- 不靠颜色单独传达状态；尊重 `prefers-reduced-motion`。
- ARIA 只在语义元素不够时补，补错比不补更糟。

## 错误处理

- 渲染错误用边界隔离，每个页面或独立面板都有兜底渲染；一个区域失败不拖垮整页。
- 错误边界只覆盖渲染与生命周期错误。异步与事件处理器里的错误要在请求层或组合函数里捕获，归一化成明确状态。
- 加载、空、错误三种状态都要有明确渲染，不能只写成功路径。
- 错误对用户可读、可重试；技术细节进日志，不进界面。
- 不吞异常。捕获后要么恢复，要么上报，要么让上层处理。
- 网络错误、权限错误、校验错误分开处理，不统一弹“操作失败”。

## 团队一致性

- 命名、目录、状态管理、请求层、错误规范统一，优先于个人写法。
- 新代码跟随项目现有约定；要改约定，先小范围试点并写进规范，不在单个需求里另起一套。
- 规范冲突时以仓库现有约定为准，并把分歧提出来，不默默各写各的。

## 完成前检查

1. 核心规则能否不渲染 UI 就测？
2. 新增交互能用键盘完成吗？焦点去哪了？
3. 加载、空、错误三条路径都实现了吗？
4. 改动有没有可测量的性能依据？
5. 异常被谁接住？用户看到什么？
