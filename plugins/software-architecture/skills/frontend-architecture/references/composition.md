# 组合

用组合表达变化，不用配置堆分支。判据：新增一种变化，是加一个组合点，还是改一个巨型组件的内部条件？

## 组合优先于配置

- 内容插槽、子元素、渲染函数、组合函数，都是把“变化的部分”交给调用方。
- 布尔参数每加一个，内部状态组合翻倍。三个布尔开关就有八种组合，其中多数没人测过。
- 同一个位置出现两种以上渲染形态，改用内容插槽或子元素，不要加 `mode`、`type`、`variant` 再写一长串 `if`。这是组合信号，不是抽象信号：抽象指提取新的共享单元，门槛仍是第三次出现。

## 常见形态

| 需求 | 做法 |
|---|---|
| 外壳固定、内容变化 | 默认内容插槽或子元素 |
| 多个具名区域 | 具名插槽或多个内容属性 |
| 行为复用、渲染不同 | 组合函数 / 自定义 hook |
| 一组组件共享隐式状态 | 复合组件（父组件提供上下文，子组件读取） |
| 同一数据不同展示 | 数据与展示分离，展示层由调用方组合 |

## 契约

组件与组合函数的接口就是契约，写清楚：

- 输入：哪些必填、哪些可选、默认值是什么。
- 输出：触发哪些事件、参数是什么、何时触发。
- 状态：加载、空、错误、禁用分别怎么表现。
- 失败：抛错、返回错误值，还是交给上层边界。

契约稳定，内部才能自由重构。接口变更要当成破坏性变更处理。

## 抽象时机

- 同一模式出现三次，且变化方向一致，再抽。
- 抽象前先写两个具体实现，看清共同点与差异点；没有两个实现，抽象就是猜。
- 抽象后做“删除测试”：删掉这层抽象，调用方会变复杂多少？不会变复杂，说明抽象没价值。
- 不为不存在的未来预留扩展点。扩展点本身也是维护成本。

## 避免继承

组件与业务逻辑用组合，不用继承层级。继承把变化锁死在类层次里，组合把变化留在调用点。

## 检查清单

1. 这个组件的布尔参数超过三个了吗？能否改成内容插槽或变体组件？
2. 新增一种形态，需要改组件内部还是加组合点？
3. 这个抽象有两个以上真实使用点吗？
4. 接口的输入、输出、错误、空状态写清楚了吗？
5. 删掉这层抽象，调用方真的会变复杂吗？
