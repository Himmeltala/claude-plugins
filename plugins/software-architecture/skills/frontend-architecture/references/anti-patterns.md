# 反模式

按症状查。每条给出原因与改法，不追求穷举。

| 症状 | 为什么坏 | 改法 |
|---|---|---|
| 什么都往全局状态容器放 | 全局状态没有生命周期，谁都能改，测试要重置整个世界 | 只放跨页面共享的业务事实；UI 临时态留在组件内 |
| 一个组件几百行，取数、转换、交互、渲染全包 | 变化原因太多，任何需求都要动它 | 拆成页面编排、业务组件、展示组件；规则下沉为纯函数 |
| 请求散落在组件里 | 无法统一处理错误、鉴权、取消、重试 | 收敛到请求层；组件只消费结果 |
| 用监听器同步两份状态 | 两个写入点，容易循环、抖动、时序错乱 | 保留一份源，另一份改为派生 |
| 组件参数越来越多，布尔开关成排 | 状态组合指数增长，内部条件难测 | 用内容插槽、子元素、变体组件表达变化 |
| 为“以后可能用到”提前抽象 | 抽象没有真实使用点，猜错后改动成本更高 | 出现第三次再抽；先写两个具体实现 |
| 业务规则写在模板或 JSX 里 | 无法单测，展示与规则一起变 | 规则抽成纯函数，模板只做展示 |
| 同一个值存两份再手动同步 | 必然出现不一致 | 单一数据源，派生另一份 |
| 参数一层层透传好几层 | 中间组件被迫知道不关心的数据 | 用上下文或组合函数就近提供 |
| 请求失败只弹一个“操作失败” | 用户不知道怎么办，排查也没有线索 | 分类归一化错误，给出可重试提示，细节进日志 |
| 捕获异常后什么都不做 | 故障被隐藏，状态可能已损坏 | 恢复、上报，或交给上层错误边界 |
| 按文件类型铺平目录 | 找一个功能要跨多个目录 | 按业务能力分目录，`shared` 只放稳定通用件 |
| `shared` 变成杂物间 | 谁都不敢删，依赖方向混乱 | 只提升被两个以上业务使用的稳定件 |
| 组件库封装过度，二次封装套二次封装 | 每层只转发参数，排查要穿多层 | 直接使用基础组件；只在有真实统一需求时封装 |
| 双向绑定同步业务状态 | 修改来源不可追踪 | 单向数据流，显式事件或状态写入方法 |

## 判断口诀

- 写入点超过一个，先合并。
- 变化原因超过一个，先拆。
- 使用点不足两个，先不抽象。
- 状态能算出来，先不存。
- 错误没人接，先补边界。
