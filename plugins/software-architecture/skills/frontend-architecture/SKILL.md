# 前端编码标准：持续管理复杂度

不是某个设计模式或框架，而是：持续管理复杂度，让代码能随需求可预测地演进。核心目标是降低认知负荷与变更成本。UI 会变、交互会变、接口会变、团队会变，所以设计围绕“变化”，而不是“一次性写对”。

真正好的前端设计，是让下一个开发者能快速看懂、安全修改、局部替换、放心测试的设计。

通用四支柱见 `software-architecture` 技能，本技能只给前端判据。

一句话公式：**清晰边界 + 单向数据流 + 最小状态 + 可组合契约 + 可测试性。**

## 一、清晰边界

- 模块边界、组件边界、状态边界、副作用边界都要明确。
- 高内聚低耦合：一个组件或模块只负责一件事，对外接口小而稳定。
- 业务逻辑不要散落在 UI 事件里，尽量沉淀为纯函数、hooks、service、store。
- 判断边界看变化原因：展示变化、交互变化、数据变化、规则变化，落在不同单元里。

## 二、可预测的数据流

- 优先单向数据流：状态变化驱动视图更新，避免隐式双向同步。
- 状态最小化：能派生就不存储，能局部就不全局。
- 一个数据只有一个写入点；视图只读，不直接改共享状态。
- 异步与副作用集中管理，不到处请求，不到处改全局状态。

### 状态放哪

从下往上选，能低不高：

| 位置 | 适用 |
|---|---|
| 组件内部状态 | 只服务当前组件，随组件销毁 |
| 父子接口 | 一层或两层传递，方向清楚 |
| 跨层级上下文 | 固定上下文：主题、当前用户、表单实例 |
| 全局状态容器 | 多个不相关页面共享、需跨路由存活 |
| URL | 刷新后应保留、可分享、可前进后退 |

## 三、可组合优于可配置与继承

- 组件用组合表达变化，不堆大量布尔参数，不用继承。
- 抽象要有稳定边界：先有两个具体实现作证据，第三次出现再抽象，不为未来臆想过度设计。
- 契约清晰：参数、事件、返回值、错误处理可预期。
- 布尔开关超过三个，或同一位置出现多种渲染形态，改用内容插槽、子元素或变体组件。

## 四、把质量约束前置

- 可测试性：核心逻辑纯函数化，UI 与业务解耦。
- 性能、可访问性、错误处理是设计约束，不是事后优化。
- 团队一致性：命名、目录、状态管理、请求层、错误规范统一，比“个人优雅”更重要。
- 加载、空、错误三条路径都要有归属，不只写成功路径。

## 分包：按功能，不按文件类型

feature-first 是判据，不是目录模板。具体结构以实际项目目录为准，不为套模板做迁移或改名。

判断两条：

1. 同一业务的变化，涉及的文件是否聚在一起？
2. 跨业务共享，是否只有一个稳定入口？

示意结构，按实际项目调整：

```text
src/
  <业务>/{组件,组合函数,请求,类型}
  shared/{通用组件,通用函数,请求基础设施}
  app/{路由,全局状态,布局}
```

不论目录叫什么，守住三条：业务内部实现不外泄；共享代码只放已被两个以上业务使用且稳定的东西；依赖方向指向稳定侧。

## 默认参考信号

以下只是触发检查的信号，不是硬规则。拆之前先确认存在两个以上独立变化原因：

- 单个组件文件超过 300 行，或参数超过 7 个，或布尔开关超过 3 个。
- 单个组合函数超过 200 行。
- 同一段逻辑第三次出现。
- 参数透传超过两层。

## 判据细则

- `references/boundaries.md`：四类边界、按功能分包、依赖方向。
- `references/data-flow.md`：单一数据源、派生、异步与错误、URL 状态。
- `references/composition.md`：内容插槽与子元素、布尔参数、契约、抽象时机。
- `references/quality-gates.md`：可测试性、性能、可访问性、错误处理、团队一致性。
- `references/anti-patterns.md`：症状、原因、改法对照。

## 完成前检查

1. 这次改动变化的是展示、交互、数据还是规则？边界对上了吗？
2. 新状态能否派生？能否局部化？只有一个写入点吗？
3. 副作用是否集中？加载、空、错误路径都实现了吗？
4. 新抽象有两个以上真实使用点吗？
5. 核心逻辑能否不渲染 UI 就测？
